The Problem — Why Finding Nearby Drivers is Hard

The naive approach: Store driver locations as (latitude, longitude). When rider requests, calculate distance to every driver, return closest. This fails at scale. With 1M drivers, you'd compute 1M distance calculations per request × 1M requests/second = unworkable.
❌
What Doesn't Work
1
Raw lat/long search
O(N) scan over all drivers — impossible at scale
2
Even-sized grid squares
Empty ocean cells. Hot cells in cities. Uneven distribution.
3
Single-resolution grid
Too small = storage explodes. Too large = poor accuracy.
✅
What Uber Built
1
H3 Hexagonal Index
Hierarchical hexagonal grid — Uber's own open-source library
2
Cell-based location storage
Drivers grouped by which H3 cell they're in. Fast lookups per cell.
3
Sort by ETA, not distance
Closest in time, not just space (traffic-aware)
02

Location Indexing — The Core Idea

The insight: Instead of "find drivers near lat/lng X,Y", reframe as "find drivers in cells covering my area". Cell lookup is O(1). Listing drivers in cells is O(small number).
🎯
The Algorithm
1
Convert rider's location to H3 cell
geoToH3(lat, lng, resolution) → cell_id
2
Get neighboring cells
kRing(cell_id, k=2) → returns rider's cell + all cells within k steps
3
Query each cell for drivers
Drivers are pre-indexed by their current cell. Lookup is O(1).
4
Calculate ETA for found drivers
Use routing engine with traffic data — not just euclidean distance
5
Sort by ETA, return top N
Closest in time wins — could be a slightly farther driver with no traffic
🔑
Cell as Sharding Key

The H3 cell identifier becomes the partition key for the location database. Drivers in the same cell live on the same database shard — making "find drivers in this cell" a single-shard query instead of a distributed scatter-gather.

The H3 Library — Uber's Open-Source Gift

What is H3: A hexagonal-shaped hierarchical geospatial indexing system created at Uber. Open-sourced in 2018. Now used by Lyft, DoorDash, Tesla, NASA — anyone with geospatial scale problems.
🌍
How H3 Sees Earth

H3 divides Earth's surface into hexagonal cells on a flat grid. Each cell gets a unique 64-bit integer identifier.

  • 122 base cells cover the entire Earth
  • 110 hexagons + 12 pentagons
  • Pentagons exist because you can't tile a sphere with only hexagons
  • H3 treats each pentagon as a "hexagon with a missing piece"
🔢
The 64-bit Cell ID

Every H3 index encodes:

// Bit layout of an H3 index

Mode          (4 bits)   = type of index
Reserved      (3 bits)   = future use
Resolution    (4 bits)   = 0-15 (16 levels)
Base cell     (7 bits)   = 0-121
Digits        (45 bits)  = path from base
              (3 bits × 15 levels)

// Example index:
0x8928308280fffff
// Resolution 9, in San Francisco
📐
Resolution Levels

H3 supports 16 resolution levels (0-15). Each level subdivides cells into 7 smaller hexagons. Choose the right resolution for your use case:

Res 0
~4.4M km²
Res 5
~250 km²
Res 9
~0.1 km²
Res 15
~1 m²
For Uber's use case: Resolution 8-9 is sweet spot. Cells are roughly the size of a small neighborhood (~0.1 km²). Enough drivers per cell for good matching, small enough for accurate proximity.

Hierarchical Grid — Why It's Brilliant

The trade-off: Small cells = high accuracy + huge storage. Big cells = low storage + poor accuracy. Hierarchical grids solve this by allowing different resolutions in different places.
🪆
How Hierarchy Works

In H3, each hexagon at resolution N is subdivided into 7 smaller hexagons at resolution N+1. This creates a parent-child relationship that you can traverse with simple bitwise operations.

┌──────────────────────┐ │ 1 Hexagon at Res 5 │ │ (~250 km²) │ └──────────┬───────────┘ │ subdivide ▼ ┌──────────────────────┐ │ 7 Hexagons at Res 6 │ │ (~36 km² each) │ └──────────┬───────────┘ │ subdivide ▼ ┌──────────────────────┐ │ 49 Hexagons at Res 7 │ │ (~5 km² each) │ └──────────────────────┘ Continue subdividing... up to Resolution 15
🗜️
Data Compression Through Mixed Resolution

Hierarchical grids enable spatial data compression. The genius: store data at different resolutions for different areas.

🌊 Ocean / Desert

Few drivers. Use low resolution (large cells). Saves storage. One cell can represent thousands of square km.

🏙️ Dense City

Many drivers. Use high resolution (small cells). Precise matching. Each cell is a city block.

⚡
The Magic Trick: Truncation

Because the H3 index encodes the full path from the base cell, you can truncate bits to find ancestor cells. This is a constant-time bitwise operation. 

// Child to parent conversion — O(1) bitwise truncation

const childCell  = 0x8928308280fffff; // Resolution 9
const parentCell = h3ToParent(childCell, 7); // Resolution 7

// Internally just zeroes out the last few digits
// No tree traversal needed!

// Use cases:
// - Aggregate driver counts by neighborhood (parent cell)
// - Switch resolution without recomputing
// - Check if a small cell is within a large region
05

Why Hexagons? Not Squares or Triangles

The geometry that wins: Hexagons are the only shape where every neighbor is equidistant from the cell's center. This makes distance calculations trivial.
Triangle
△
3 edge-neighbors, 9 vertex-neighbors

❌ 3 different distances between cells

Square
□
4 edge-neighbors, 4 vertex-neighbors

❌ 2 different distances (edge vs diagonal)

Hexagon
⬡
6 edge-neighbors — all equal

✅ 1 uniform distance

📏
Why Uniform Neighbor Distance Matters

In a hexagonal grid, all 6 neighbors of any cell are at the same distance from the cell's center. This means:

  • Distance calculations require no extra coefficients
  • kRing(cell, k=1) returns 6 cells at distance 1 — clean and predictable
  • Spatial relationships are uniform — easier to reason about
  • Better approximates circles (vehicle range, delivery radius)
⚠️
The Trade-off: Imperfect Subdivision

Hexagons can't be perfectly subdivided into smaller hexagons (unlike squares, which split into 4 perfect squares). H3 handles this by subdividing each hexagon into 7 smaller hexagons with a known small error. Child hexagons are slightly rotated to fit the parent shape. The error is bounded and acceptable for proximity work.

H3 Core Algorithms — The API You'll Use

📍
geoToH3() — Coordinate to Cell

Convert latitude/longitude to a cell ID at a specific resolution. 

// Find the H3 cell containing a point
const cellId = h3.geoToH3(
  37.7749,   // latitude (San Francisco)
  -122.4194, // longitude
  9          // resolution (0-15)
);

// Returns: "8928308280fffff"
// This is the cell ID where the point is located

// Used when:
// - Driver updates location → which cell are they in now?
// - Rider requests ride → which cell are they in?
🎯
kRing() — Find Neighbors

Returns all cells within k steps of a center cell. Critical for proximity search. 

// Find all cells within 2 steps
const nearbyCells = h3.kRing("8928308280fffff", 2);

// Returns 19 cells:
//   1 center cell
//   6 cells at distance 1
//   12 cells at distance 2
//   Total: 1 + 6 + 12 = 19 cells

// To find drivers near a rider:
const riderCell = h3.geoToH3(rider.lat, rider.lng, 9);
const searchCells = h3.kRing(riderCell, 2);
const nearbyDrivers = await db.query(`
  SELECT * FROM drivers
  WHERE current_cell IN ($1)
  AND status = 'available'
`, [searchCells]);
🪆
h3ToParent() / h3ToChildren()

Navigate the resolution hierarchy. Useful for aggregation and adaptive resolution. 

// Get parent cell at lower resolution
const neighborhood = h3.h3ToParent(blockCell, 7);
// Aggregate drivers by neighborhood:
//   SELECT count(*) FROM drivers GROUP BY parent_cell

// Get all child cells at higher resolution
const blocks = h3.h3ToChildren(neighborhood, 9);
// Returns 7 child cells (neighborhood subdivided)

// Used for:
// - Surge pricing zones (neighborhood-level)
// - Driver heatmaps
// - Search radius expansion (start small, expand outward)

Location Storage — Cassandra + Redis

The dual-storage strategy: Each driver app sends location every few seconds. We need to absorb massive writes (Cassandra) AND serve fast reads for matching (Redis). Use both.
DRIVER APPS (1M+ drivers) │ │ Location ping every 4s ▼ ┌─────────────────────┐ │ LOCATION SERVICE │ └──────────┬──────────┘ │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ REDIS │ │ CASSANDRA │ │ KAFKA │ │ (recent) │ │ (history) │ │ (events) │ │ │ │ │ │ │ │ Read path │ │ Write path │ │ Streaming │ │ for match │ │ for analy. │ │ for ML/ │ │ │ │ │ │ pricing │ └────────────┘ └────────────┘ └────────────┘
⚡
Redis — Read Layer

Stores recent driver locations for fast matching. 

# Key per H3 cell, value = set of drivers

SADD cell:8928308280fffff:drivers
  "driver_001"
  "driver_042"
  "driver_077"

EXPIRE cell:8928308280fffff:drivers 60

# When driver moves to new cell:
SREM cell:OLD_CELL:drivers "driver_001"
SADD cell:NEW_CELL:drivers "driver_001"

# Driver's current location:
HSET driver:001:location
  cell "8928308280fffff"
  lat  37.7749
  lng  -122.4194
  ts   1699189200000
💾
Cassandra — Write Layer

Stores complete location history for analytics, ML training, surge pricing. 

CREATE TABLE location_history (
  driver_id   UUID,
  timestamp   TIMESTAMP,
  lat         DOUBLE,
  lng         DOUBLE,
  h3_cell     TEXT,
  speed_mps   DOUBLE,
  heading_deg DOUBLE,
  accuracy_m  DOUBLE,
  source      TEXT,  -- 'gps', 'network', 'fused'
  PRIMARY KEY ((driver_id), timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC);

-- Sharded by driver_id
-- Each driver's history = one wide row
-- Optimized for time-series writes
📊
Why This Split Works
WorkloadBest ToolWhy
Match queries (read) Redis Microsecond lookup; the bottleneck of "find nearby drivers"
Location pings (write) Cassandra Optimized for high write throughput, sharded by driver
Historical analytics Cassandra Time-series data, append-only, queryable by driver
Real-time events Kafka Streams to ML pipelines, surge pricing, fraud detection

Map Matching — Cleaning Noisy GPS

The reality: GPS is noisy. A driver in a downtown street with skyscrapers might appear to be 50 meters off the road. In tunnels, the signal vanishes. Without correction, the system thinks drivers are off-road or teleporting.
🛰️
What Goes Wrong With Raw GPS
1
Multipath errors in cities
GPS signals bounce off buildings. Apparent position is 10-50m off.
2
Tunnels & underpasses
No signal at all. Driver "disappears" for 30+ seconds.
3
Low accuracy in bad weather
Cloud cover degrades signal. Reported accuracy radius balloons.
4
Sparse sampling
If app saves battery, pings might be every 30s. Between pings = blind.
🗺️
Map Matching — The Fix

Map matching takes the messy GPS sequence and snaps it to actual road segments. The output: a sequence of road segments the driver actually traveled.

RAW GPS PINGS MAP-MATCHED POSITION (noisy, off-road) → (snapped to roads) Ping 1: 37.7749, -122.4194 → Road segment: Market St Ping 2: 37.7751, -122.4191 → Road segment: Market St Ping 3: 37.7754, -122.4188 → Road segment: Market St (signal lost in tunnel) (interpolated based on speed + direction) Ping 4: 37.7758, -122.4180 → Road segment: 5th St
🔄
Storage Pattern: Buffer in Redis, Match, Persist
1
Raw pings arrive every few seconds
Buffered in Redis (recent N pings per driver)
2
Map matching runs on buffered pings
Needs multiple pings to determine direction + snap correctly
3
Matched road segments stored separately
Separate Cassandra schema. Used for ETA, billing, analytics.
4
Raw GPS also kept
For debugging, ML training, disputed-trip resolution

Scalability — How Uber Hits 1M Req/Sec

The numbers: 1 million proximity queries per second. Each must complete in under 100ms. The system relies on H3-based sharding, aggressive caching, and read-write separation.
🔀
Sharding by H3 Cell

The H3 cell identifier becomes the natural sharding key. Drivers in the same cell live on the same shard. Queries for nearby drivers hit a small number of shards (one per cell in the search radius). 

// Sharding by H3 parent cell (low resolution = bigger shards)

shard_id = h3.h3ToParent(driver_cell, RES_5) % NUM_SHARDS;

// Why parent cell?
// - Cells in same neighborhood end up on same shard
// - kRing queries hit fewer shards (good for performance)
// - Driver moves within neighborhood = stays on same shard
// - Cross-shard queries only when crossing big boundaries
⚡
Multi-Layer Cache Strategy
LayerStoresTTLPurpose
App-local cache Recent match results 5s Reduce duplicate queries
Redis (per-cell) Driver sets by cell 60s Hot match path
Redis (per-driver) Driver's current cell 30s Fast location lookup
Cassandra Historical pings ∞ (TTL by policy) Analytics, ML, billing
🌍
Geographic Data Center Distribution

Drivers and riders in the same city naturally land on the same regional data center. Cross-region queries are rare (you don't book a ride in Tokyo while standing in NYC). This makes data center co-location work brilliantly with H3 cell-based sharding.

🎯
The Complete Request Flow
1
Rider opens app, requests nearby cars
Request goes to closest regional data center
2
Convert rider lat/lng to H3 cell at Res 9
Constant-time operation, no I/O
3
kRing(cell, k=2) → 19 nearby cells
Covers area ~3km radius around rider
4
Query Redis for drivers in those 19 cells
Parallel SMEMBERS on each cell key. Result: list of driver IDs.
5
Fetch driver details + map-matched positions
Filter by status (available), product (UberX vs Black)
6
Calculate ETA for each candidate
Routing engine with real-time traffic
7
Sort by ETA, return top N to rider
Total time budget: under 100ms

🎯 Interview Follow-Up Questions
Why not just use PostGIS / a geospatial database?
PostGIS works great at small scale. But at 1M req/sec, the locking overhead and disk I/O become bottlenecks. H3 + Redis lets you do everything in-memory with simple data structures (sets keyed by cell). PostGIS adds 10-100ms latency where H3 adds microseconds.
What happens when a driver crosses a cell boundary?
On every location update: compute new H3 cell. If different from previous: SREM driver from old cell's set, SADD to new cell's set. Two Redis operations, atomic via MULTI/EXEC. Then update driver:{id}:location hash with new cell.
How do you handle the pentagon cells?
12 of 122 base cells are pentagons (centered on poles + 10 in tundra/ocean areas). Almost no Uber traffic there. H3 has special handling but for typical use cases, pentagons can be ignored. Distance calculations near pentagons have slight distortion — bounded and well-documented.
How do you scale the proximity service horizontally?
Shard by H3 parent cell (low resolution → big regions). Each shard handles a city or region. Riders/drivers in same area land on same shard. Cross-shard queries only when search radius crosses shard boundary — rare and manageable.
What if there are no drivers in nearby cells?
Expand the search: kRing(cell, k=3), then k=4, etc. Or go up a resolution: query at parent cell level (covers larger area). Cap the expansion — if no drivers within 5km, return "no drivers available" rather than wait forever.
How does this differ from Tinder's S2-based location matching?
S2 (Google) uses square cells on a curved surface. H3 (Uber) uses hexagons on a flat projection. Both are hierarchical. H3's hexagons have equal-distance neighbors (better for proximity). S2's squares preserve curvature better (better for global queries). Different trade-offs for different use cases.
💡
One Thing to Remember

The hard part of "find nearby drivers" isn't the math — it's the data structure. Once you index drivers by H3 cells instead of raw lat/lng, the problem transforms:

  • From O(N) distance scan → O(1) cell lookup
  • From single-point search → bounded area search via kRing
  • From hot spots → naturally sharded by geography
  • From distance approximation → uniform hexagonal grid

This is the system design lesson: When you're stuck on performance, change the data structure. The right index turns an impossible query into an obvious one.
