Why WebSockets? The Protocol Decision

The core insight: Real-time messaging needs bidirectional, persistent connections. HTTP request/response model doesn't fit. WebSockets give us a connection that stays open, where both client AND server can push data anytime.
📡 Three Approaches Compared
❌ Polling — Wasteful

Client asks "any new messages?" every few seconds.

  • Wastes bandwidth — most requests return nothing
  • Adds latency — message arrives, must wait until next poll
  • Burns server resources with empty checks
⚠️ Long Polling — Better but Flawed

Client opens request, server holds it until there's a message or timeout.

  • Constantly opening/closing connections (HTTP handshake overhead)
  • Each message needs full handshake cycle
  • Idle connections still consume memory + thread slots
  • At scale, connection lifecycle management dominates
✅ WebSockets — What We Use

One persistent bidirectional connection that stays open.

  • Handshake happens once at connection open
  • Both client and server can push data anytime
  • Minimal overhead per message
  • Message latency = network RTT (no protocol overhead)
✅ WebSocket Pros
  • Instant message delivery
  • Bidirectional — server can push
  • Low bandwidth per message
  • No protocol overhead after open
⚠️ WebSocket Cons
  • Needs special load balancers (L4)
  • More memory per connection
  • Connection state must be tracked
  • Harder to debug than HTTP
💓
Handling Idle Connections — Heartbeats

What if user opens WhatsApp but doesn't send messages for hours? The connection stays open but idle, consuming memory. Zombie connections accumulate. Solution:

1
Client sends ping every 30 seconds
Lightweight message: just {"type": "heartbeat"}
2
Server responds with pong
Confirms connection is alive
3
No heartbeat for 60 seconds → connection closed
Server assumes network died or app backgrounded. Frees resources.

Service Discovery — Servers That Don't Stand Still

The problem: In production, chat servers come and go. They crash, get deployed, autoscale. Hardcoding IPs doesn't work when instances are ephemeral. We need a registry that knows what's currently alive.
📋
Registration Flow
1
Chat server boots up
e.g., 10.0.1.45:8080
2
Registers with Consul
Service name + instance ID + health endpoint + metadata
3
Sends heartbeat every 10s
Proves it's alive and ready
4
If heartbeat stops, marked unhealthy
After 30s (3 missed beats). Removed from rotation.
🔍
Discovery Flow
1
Load Balancer asks Consul
"Give me all healthy chat-server instances"
2
Consul returns list
[10.0.1.45:8080, 10.0.1.67:8080, ...]
3
LB updates routing table
New connections distributed to healthy servers
4
LB watches Consul for changes
Auto-updates when servers come/go
The big win: Deploy new servers — they auto-register. Kill a server — auto-removed. No manual config updates. Solves the problem of "how does the load balancer find new servers?" at scale.

Data Models — Choosing the Right Database for Each Job

👤
Users Table — SQL (PostgreSQL)

User profiles change rarely but need ACID guarantees (uniqueness on phone numbers, etc.)

CREATE TABLE users (
  user_id        UUID         PRIMARY KEY,
  phone_number   VARCHAR(20)  UNIQUE NOT NULL,
  display_name   VARCHAR(100),
  profile_picture VARCHAR(512),
  status_message VARCHAR(255),
  created_at     TIMESTAMP    DEFAULT NOW(),
  last_seen      TIMESTAMP,
  public_key     TEXT,                -- for E2E encryption
  INDEX (phone_number),
  INDEX (last_seen)
);
💬
Messages Table — NoSQL (Cassandra)

Massive write throughput. Simple query patterns (by conversation + time). Cassandra wide-rows fit perfectly.

CREATE TABLE messages (
  conversation_id UUID,           -- Partition key (1:1 chat or group)
  message_id      TIMEUUID,       -- Clustering key — natural time ordering
  sender_id       UUID,
  receiver_id     UUID,           -- For 1:1; null for groups
  content         TEXT,           -- Encrypted at rest
  media_url       TEXT,           -- S3/CDN URL if present
  message_type    TEXT,           -- 'text', 'image', 'video', 'audio'
  status          TEXT,           -- 'sent', 'delivered', 'read'
  reply_to        TIMEUUID,
  created_at      TIMESTAMP,
  PRIMARY KEY ((conversation_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
-- Most recent messages first → efficient pagination
👥
Groups Table — SQL

Group metadata + membership. Updates are rare (creating group, adding members), but need ACID.

CREATE TABLE groups (
  group_id     UUID         PRIMARY KEY,
  name         VARCHAR(100) NOT NULL,
  description  TEXT,
  admin_id     UUID         REFERENCES users(user_id),
  created_at   TIMESTAMP    DEFAULT NOW(),
  group_icon   VARCHAR(512)
);

CREATE TABLE group_members (
  group_id     UUID,
  user_id      UUID,
  joined_at    TIMESTAMP,
  role         VARCHAR(20),   -- 'admin', 'member'
  PRIMARY KEY (group_id, user_id)
);
⚡
User Connection Registry — Redis

Maps user_id → chat server they're connected to. Microsecond lookups for routing decisions.

# Key: user:{user_id}:connection
# Value: hash with connection details

HSET user:123:connection
  server_id     "chat-server-abc123"
  server_ip     "10.0.1.45"
  device_id     "phone-abc"
  connected_at  "1699189200000"
  last_activity "1699189250000"

EXPIRE user:123:connection 90   # TTL: 90 seconds, refreshed by heartbeat
📥
Message Inbox — Redis

Per-user queue of pending messages while they're offline. Sorted by timestamp.

# Key: inbox:{user_id}
# Value: sorted set of message IDs

ZADD inbox:123
  1699189200000 "msg_001"
  1699189250000 "msg_002"
  1699189300000 "msg_003"

# When user comes online, fetch all pending
ZRANGE inbox:123 0 -1 WITHSCORES

# After delivery, remove
ZREM inbox:123 "msg_001"

CLIENT → SERVER

    "content": "Meeting at 3 PM",
    "media_url": null,
    "timestamp": 1699189200000

}
SERVER FANS OUT TO ALL MEMBERS
{
  "type": "group_message",
  "payload": {
    "message_id": "20241105120000000005",
    "group_id": "group_789",
    "sender_id": "123",
    "content": "Meeting at 3 PM",
    "timestamp": 1699189200123
  }
}
Why 100-member limit? For each group message, server fans out to ALL members (online or queued for offline). 1 message in a 100-person group = 100 deliveries. In a 10K-person group it'd be 10K deliveries. The 100 cap keeps fan-out manageable.

Presence Service — Online/Offline Status

Why a dedicated service: Presence is read-heavy (everyone wants to see "Last seen" of contacts) and write-heavy (heartbeats from millions of users). Mixing it with chat servers would slow down message delivery.
💓
How Presence Tracking Works
1
Client sends heartbeat every 5 seconds
Lightweight WS message proving the app is in foreground
2
Presence service updates Redis
SET user:123:status "online", EXPIRE 10s. Auto-expires if heartbeats stop.
3
Publishes change to subscribers
Pub/sub channel notifies anyone watching this user's status
4
Contacts get pushed updates
Other users in same chats receive presence change via their WS connection
5
When heartbeat stops, status flips offline
Redis key expires → "Last seen" timestamp displayed instead
📊
Privacy Considerations
Per-user privacy settings

Show "Last seen" to: Everyone, Contacts only, Specific people, Nobody. Stored per-user.

Server-side filtering

Before sending presence updates, presence service checks if requester has permission to see. Privacy enforced at API layer, not client.

Offline Message Delivery — The Hard Part

The reality: Recipient is offline 90% of the time. Network drops. Battery dies. Airplane mode. The system must reliably deliver messages whenever they come back online — even days later.
📬
Complete Delivery Flow
1
Sender's message arrives at chat server
Via persistent WebSocket connection
2
Server checks Redis: is recipient online?
Microsecond lookup: GET user:{receiver_id}:connection
3a
If ONLINE → push directly via WS
Get recipient's chat server from Redis. Forward message. Wait for delivery ACK.
3b
If OFFLINE → store in inbox + send push
ZADD inbox:{receiver_id}. Send push notification via APNs/FCM. Message persists for up to 30 days.
4
User comes back online
App connects, sends auth, receives unread_count in auth_success.
5
Server flushes inbox to client
ZRANGE inbox:{user_id} 0 -1 → push all messages via WS in order.
6
Client ACKs each message
Server removes ACKed messages from inbox. If client fails to ACK, redelivery on next connect.
🔔
Push Notifications — APNs & FCM

Even with WebSockets, mobile OSes kill background processes to save battery. When that happens, we need OS-level push notifications to wake up the app.

PlatformServiceWhat It Does
iOSAPNs (Apple Push Notification service)Wakes app, displays banner, plays sound
AndroidFCM (Firebase Cloud Messaging)Wakes app, displays notification
WebWeb Push APIBrowser-level notifications
Important: Push notification ≠ the message itself. It's just a wake-up signal. The actual message comes via WebSocket once the app reopens. This is why messages don't disappear if you swipe away a notification.

Media Uploads — Without Killing the Servers

The principle: Chat servers handle text messages (KBs). Blob storage + CDN handle media (MBs to GBs). Never mix the two. A single 100MB video upload would block thousands of text messages.
📤
Upload Flow
1
Client requests upload URL via REST
POST /api/media/upload — tells server file type and size
2
Server generates pre-signed S3 URL
Temporary URL valid for 1 hour. Returns media_id.
3
Client uploads directly to S3
Multipart upload for large files. Resumable on failure. Bypasses chat servers entirely.
4
Client sends WS message with media_url
Just a reference: {media_url: "https://cdn.../media_xyz789"}
5
Recipient downloads via CDN
Same CDN URL → cached at edge nodes → fast download globally
🔐
End-to-End Encryption Considerations

Media is E2E encrypted before upload. Server never sees plaintext:

  1. Client generates random AES-256 key
  2. Encrypts the media file with that key
  3. Uploads encrypted blob to S3
  4. Encrypts the AES key with recipient's public key
  5. Sends encrypted key + S3 URL via WS message
  6. Recipient decrypts AES key with their private key, then decrypts media
The result: Even WhatsApp employees with full S3 access can't read your media. They only have encrypted blobs with no keys.
📊
Media Optimization
Media TypeOptimization
PhotosAuto-compressed to ~80% quality on client, then uploaded
VideosTranscoded to 720p MP4, lower bitrates. Significant size reduction.
AudioOpus codec, mono, low bitrate (~16kbps for voice messages)
DocumentsSent as-is, max 100MB per file

Group Chats — Fan-Out at Scale

The challenge: One sender, N receivers. A 100-person group means 1 message = 100 deliveries, 100 ACKs, 100 read receipts. Multiply by millions of active groups and the math gets brutal.
📨
Fan-Out Strategy

When a group message arrives, the server must deliver it to every member. Two main approaches:

✅ Fan-Out on Write (WhatsApp)
  • Server iterates all group members
  • For each: check online → push WS, or queue in inbox
  • Higher write cost but instant delivery
  • Works well when group sizes are capped
❌ Fan-Out on Read
  • Message stored once, members pull on connect
  • Worse for real-time messaging
  • Members might miss messages mid-session
  • Better suited to feeds (Twitter), not chat
⚡
Efficient Fan-Out Implementation
// Pseudo-code for group message fan-out

async function handleGroupMessage(groupId, message) {
  // 1. Save message once (not per-member)
  await cassandra.insert('messages', {
    conversation_id: groupId,
    message_id: generateTimeUUID(),
    content: message.content
  });

  // 2. Get all group members (cached in Redis)
  const members = await redis.smembers(`group:${groupId}:members`);

  // 3. For each member, check online status + deliver
  await Promise.all(members.map(async (userId) => {
    if (userId === message.senderId) return;  // don't echo

    const conn = await redis.hgetall(`user:${userId}:connection`);

    if (conn?.server_id) {
      // Online — push via WS
      await chatServers[conn.server_id].push(userId, message);
    } else {
      // Offline — queue in inbox + push notification
      await redis.zadd(`inbox:${userId}`, Date.now(), message.id);
      await notificationService.send(userId, message);
    }
  }));
}
🔐
Group Encryption Challenge

E2E encryption with groups is harder than 1:1. Naive approach (encrypt for each member separately) doesn't scale. Solution: Sender Keys.

  1. Sender generates a Sender Key (AES-256) for the group
  2. Encrypts the Sender Key separately for each member (using their public key)
  3. Distributes encrypted keys once per group session
  4. Then messages use the shared Sender Key (much cheaper than encrypting per-message-per-member)
Why this works: Key distribution happens rarely (only when members join/leave). Messages encrypt once, decrypt N times. Much more efficient than encrypting once per member per message.

Cheat Sheet — Key Decisions

Use this in interviews to quickly justify your design choices. Each decision answers a "why" question.

🎯 Common Interview Follow-Up Questions
How do you handle message ordering across devices?
Use server-assigned timestamps (TIMEUUID in Cassandra). Client sorts by timestamp, not arrival order. Devices sync via shared message_id sequence.
What if Redis goes down?
Multi-master Redis Cluster with replication. If a node fails, replicas take over. User connection registry is rebuilt as users reconnect (it's transient state).
How do you prevent duplicate messages?
client_message_id is the idempotency key. Server checks: have I seen this ID? If yes, return the existing message_id. If no, process and store.
How do you scale to 50M concurrent connections?
Each chat server handles ~100K connections. 50M / 100K = 500 chat servers needed. Add more behind the load balancer. Auto-scale based on connection count.
How do you handle a "last seen" timestamp without a heartbeat per query?
Heartbeat updates Redis. Last seen = last heartbeat timestamp. Read it directly. No per-query overhead.
What about multi-device support?
Same user can have multiple WS connections (phone + web + desktop). Server fans out to all active devices. Redis stores list of connections per user_id.
💡
One Thing to Remember

WhatsApp's architecture is brilliant because it does less, not more. Messages are tiny. Storage is temporary. Media bypasses servers via CDN. Fan-out is capped by group size. Each design choice removes work, not adds it.

The result: 2 billion users, 100 billion messages/day, originally ~50 engineers. Efficiency through elegant design — not throwing hardware at problems.
