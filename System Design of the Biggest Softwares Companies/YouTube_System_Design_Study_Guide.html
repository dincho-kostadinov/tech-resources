Interview Questions to Ask First

Pro tip: Always start by asking clarifying questions. This shows you think about constraints before designing. Interviewers expect this from Senior+ engineers.
❓ What scale are we designing for?
Answer: 1 million uploads per day, 100 million DAU.
Why: Drives sharding, partitioning, and caching decisions Insight: Shows understanding of capacity planning
❓ What is the read-to-write ratio?
Answer: About 100 views for every 1 upload.
Why: Design heavily favors caching and streaming optimization Insight: Shows awareness of workload patterns
❓ What is the maximum video file size?
Answer: 256 GB.
Why: Forces you to use multipart uploads and chunking Insight: Shows you consider edge cases
❓ What video formats and resolutions do we support?
Answer: MP4, AVI, MOV — from 240p to 4K.
Why: Needs a transcoding pipeline with multiple output renditions Insight: Shows attention to real-world constraints
❓ What's the target latency for first frame?
Answer: Under 500ms.
Why: Requires CDN edge caching and adaptive streaming Insight: Shows focus on user experience
❓ Is eventual consistency acceptable for new uploads?
Answer: Yes — users can wait 10-30 minutes for transcoding.
Why: Availability over strict immediacy (CAP theorem) Insight: Shows distributed systems knowledge

06

Transcoding Pipeline

1
Upload Complete → S3 Event Fired
When the raw video lands in S3, an event is published to Kafka topic video_uploads. The upload service is done — its job is complete.
2
Kafka Queue — 256 Partitions [generic — real YouTube uses Google Pub/Sub]
Partition key = video_id % 256. This ensures the same video always goes to the same partition — guaranteeing ordering and preventing double-processing.
3
5,000 Transcoding Workers Pull from Queue
Workers distributed across data centers. Each has 8 CPUs, 32GB RAM, 500GB SSD scratch space. Consumer group: transcoding_workers.
4
FFmpeg Transcodes to 6 Resolutions in Parallel [generic — real YouTube uses custom VCU hardware + VP9/AV1]
240p, 480p, 720p, 1080p, 2K, 4K. Each is split into 4-second segments (industry standard for VOD). Real YouTube uses VP9 and AV1 codecs.
5
Segments Uploaded to S3 + CDN Pushed
Path: s3://yt-processed/{video_id}/{resolution}/segment-{n}.ts
6
Database Updated → Status = 'ready'
Metadata saved, manifest generated, Redis cache invalidated. Video becomes searchable and streamable.

Adaptive Bitrate Streaming (HLS / DASH)

Key concept: YouTube uses BOTH HLS and DASH. HLS (.m3u8) for Apple devices and Safari. DASH (.mpd) for Android and Chrome. Both work by splitting video into small segments and letting the player switch quality levels on the fly.
🍎
HLS — HTTP Live Streaming
  • Created by Apple in 2009
  • Manifest file: .m3u8 (plaintext)
  • Segments: .ts files (2-6 sec each)
  • Native on iOS, macOS, Safari
  • Supports LL-HLS (2-3 sec latency)
🤖
DASH — Dynamic Adaptive
  • Open standard by MPEG (2012)
  • Manifest file: .mpd (XML)
  • Supports VP9 and AV1 codecs
  • Native on Android, Chrome
  • Used by YouTube on non-Apple devices
How Adaptive Bitrate Works — Step by Step
1
Player fetches master manifest from CDN
Gets list of all available resolutions and their bandwidths (240p = 400kbps, 4K = 15Mbps)
2
Player measures available bandwidth
Downloads a test segment, measures download time, estimates available bandwidth
3
Player selects matching quality rendition
If bandwidth = 3Mbps → selects 720p. Fetches that rendition's playlist file.
4
Player downloads segments ahead of time
Typically buffers 15-30 seconds ahead. If network drops, switches to lower quality immediately.
5
Quality switches happen at segment boundaries
Every 4 seconds the player can switch quality — seamlessly and without rebuffering.

Database Architecture & Sharding

Real YouTube fact: YouTube uses Vitess — a sharding middleware on top of MySQL (not PostgreSQL!). It was built by YouTube engineers and open-sourced. It handles horizontal sharding transparently, so app code still writes SQL queries. In this guide we use PostgreSQL syntax for clarity, but the real YouTube runs sharded MySQL.
🗄️
Why Shard by video_id?

✅ Why it works

  • Videos are append-only (no updates)
  • Every query knows video_id
  • Even distribution (UUID hash)
  • No hot shards from viral videos
  • Co-location: segments live on same shard

❌ Why NOT user_id

  • Popular creators = hot shard problem
  • "Get all videos by user" = scan ALL shards
  • Scatter-gather is expensive
  • Uneven distribution
SHARDING FORMULA
// Consistent hash to determine which shard
shard_number = CRC32(video_id) % 256

// Example
video_id = "vid_8xKp2mNqRs"
crc32(video_id) = 0x1F4A8B2C
shard = 0x1F4A8B2C % 256 = 44

// This video lives on shard_044
// DB connection string: mysql://shard044.yt.internal:3306/videos
DATABASE SCHEMA — KEY TABLES
-- Sharded by video_id (256 shards)
CREATE TABLE videos (
  video_id    VARCHAR(20)  PRIMARY KEY,        -- Shard key
  uploader_id VARCHAR(20)  NOT NULL,
  title       VARCHAR(255) NOT NULL,
  status      ENUM('uploading', 'transcoding', 'ready', 'failed'),
  created_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  INDEX (uploader_id, created_at),   -- User's videos timeline
  INDEX (status, created_at)         -- Filter by processing status
);

-- Co-located with videos table (same shard!)
CREATE TABLE video_segments (
  segment_id  VARCHAR(36)  PRIMARY KEY,
  video_id    VARCHAR(20)  NOT NULL,             -- Same shard as videos
  resolution  ENUM('240p', '480p', '720p', '1080p', '4k'),
  segment_num INT          NOT NULL,
  s3_path     VARCHAR(512) NOT NULL,             -- s3://bucket/vid/.../seg-001.ts
  UNIQUE (video_id, resolution, segment_num)  -- Idempotency!
);

-- Separate shard group (sharded by user_id)
CREATE TABLE users (
  user_id     VARCHAR(20)  PRIMARY KEY,
  username    VARCHAR(255) UNIQUE NOT NULL,
  email       VARCHAR(255) UNIQUE NOT NULL,
  plan        ENUM('free', 'premium', 'pro')
);

Caching Strategy — 3 Layers

1
Layer 1: CDN Edge Cache — Terabytes globally
Video segments + manifest files cached at 3,000+ edge locations. TTL = 24 hours. Top 1% of videos get 95% hit rate. Saves billions of origin requests per day.
2
Layer 2: Redis Cluster — Metadata Cache
Video metadata, manifests, user profiles, trending lists. TTL = 1 hour. Write-through pattern: update Redis on every DB write. 256 nodes with consistent hashing.
3
Layer 3: Client-Side Cache — Device Storage
Downloaded segments stored on device. Enables offline playback, instant replay. Last ~1GB of watched content cached locally (configurable).
REDIS KEY PATTERNS
// Video metadata — expires 1 hour
video:vid_8xKp2mNqRs:meta    → { title, duration, view_count, likes }
video:vid_8xKp2mNqRs:hls     → { manifest_content }

// User data — expires 24 hours
user:usr_4kNpRmQs:profile   → { name, plan, storage_used }

// Trending — recomputed every 5 minutes
trending:global:daily       → [ vid_001, vid_002, ..., vid_100 ]
trending:US:weekly          → [ vid_005, vid_012, ... ]

// Real-time view counter (not DB — Redis atomic increment)
views:vid_8xKp2mNqRs        → 1482930   // INCR every view

Multi-Region Deployment

US-EAST

Primary write region. All writes go here first. Single source of truth.

PRIMARYWrites
US-WEST / EU

Read replicas. Lag <150ms from US-EAST. Handle reads locally.

REPLICAReads
APAC (SG + SYD)

Read replicas. Lag ~250-300ms. Transcoding workers for local uploads.

REPLICATranscoding
Read-after-write consistency: When a user uploads a video in Singapore, they are redirected to read from the APAC replica after the write to US-EAST completes. This ensures they immediately see their own upload (250ms lag) while other users get eventual consistency.

Architectural Trade-offs

⚖️ Eventual Consistency vs Strong Consistency

Choice made: Eventual consistency for video metadata

✅ Why Eventual
  • Higher availability (read from any replica)
  • Faster responses globally
  • Scale to 2.5B users
  • 60-300ms lag is fine for video
❌ Costs
  • Users may see stale view counts
  • New uploads delay 60-300ms
  • Complex cache invalidation
⚖️ Pre-generate All Resolutions vs On-demand

Choice made: Pre-generate all 6 resolutions

✅ Why Pre-generate
  • Zero wait for any quality level
  • Predictable latency for 4K viewers
  • Simpler CDN caching
❌ Costs
  • 6× storage cost
  • 6× transcoding time
  • Most 4K is never watched
⚖️ Async Transcoding vs Sync Transcoding

Choice made: Async (10-30 min delay)

✅ Why Async
  • Upload completes immediately
  • Transcoding scales independently
  • Kafka enables automatic retries
  • Batch during off-peak hours
❌ Costs
  • Video not immediately watchable
  • More operational complexity
  • Must monitor queue depth
⚖️ S3 vs Custom Storage

Real YouTube uses Colossus (Google's internal storage)

✅ Why S3 (for most)
  • Zero operational overhead
  • 11 nines durability built-in
  • No engineering needed
❌ Costs
  • $0.085/GB egress = expensive at scale
  • Vendor lock-in
  • YouTube saves $100M+/yr with Colossus

🌐

Критично: Chunked Upload

256GB файл не може да се качи наведнъж. Разбиваме на chunks:

// Client-side chunking
const CHUNK_SIZE = 10 * 1024 * 1024; // 10MB

async function uploadInChunks(file, uploadUrl) {
  const totalChunks = Math.ceil(
    file.size / CHUNK_SIZE
  );

  for (let i = 0; i < totalChunks; i++) {
    const chunk = file.slice(
      i * CHUNK_SIZE,
      (i + 1) * CHUNK_SIZE
    );
    await uploadChunk(uploadUrl, chunk, i);
    // Save progress → resume on failure
    localStorage.setItem(
      `upload_${videoId}_progress`, i
    );
  }
}

Rate Limiting имплементация
// Sliding window rate limiter
// Redis Sorted Set — O(log N)

async function checkRateLimit(userId) {
  const key = `rate:${userId}`;
  const now = Date.now();
  const window = 60000; // 1 минута
  const limit = 100;  // free tier

  await redis.zremrangebyscore(
    key, 0, now - window  // Изтрий старите
  );

  const count = await redis.zcard(key);

  if (count >= limit) {
    throw new Error('Rate limit exceeded');
  }

  await redis.zadd(key, now, now);
  await redis.expire(key, 60);
}
LAYER 4

Microservices Layer

Защо микросервизи? Upload Service трябва 200 инстанции при пик. Search Service трябва 20. Transcoding Workers трябва 5000. Ако всичко е в един монолит — или разхищаваме ресурси, или всичко е bottleneck.
📤 Upload Service

Единствената отговорност: генерира pre-signed S3 URL и записва metadata. Не докосва нито един байт видео.

1
Validate request
File size ≤ 256GB, content-type video/*, user has storage quota
2
Generate video_id + pre-signed URL
S3 URL expires в 1 час. Клиентът качва директно.
3
S3 Event → Kafka
Когато клиентът финишира upload-а, S3 пуска event → Kafka topic video_uploads.
// Upload Service — POST /v1/videos
app.post('/v1/videos', async (req, res) => {
  const { title, fileSize, contentType } = req.body;
  const userId = req.headers['x-user-id']; // от Gateway

  // 1. Check storage quota
  const user = await db.getUser(userId);
  if (user.storageUsed + fileSize > user.quota) {
    return res.status(413).json({
      error: 'Storage quota exceeded'
    });
  }

  // 2. Generate pre-signed S3 URL
  const videoId = nanoid(12);
  const uploadUrl = await s3.presign({
    bucket: 'yt-raw',
    key: `raw/${videoId}`,
    expires: 3600,
    contentType,
    maxSize: fileSize
  });

  // 3. Save to DB — status: 'uploading'
  await db.insertVideo({
    id: videoId, title,
    uploaderId: userId,
    status: 'uploading'
  });

  res.status(201).json({ videoId, uploadUrl });
});
🎬 Transcoding Service

5,000 worker инстанции. Всяка дърпа job от Kafka, транскодира, качва сегментите в S3.

Kafka Partition (video_id % 256) │ ▼ ┌─────────────────────┐ │ Transcoding Worker │ │ │ │ 1. Download from S3 │ │ 2. FFmpeg → 6 res. │ │ 3. Segment to 4s .ts │ │ 4. Upload to S3 │ │ 5. Generate manifest │ │ 6. Update DB │ │ 7. Invalidate CDN │ └─────────────────────┘
Idempotency: Ако worker-ът crash-не и job-ът се преиграе — проверяваме дали сегментите вече са в S3 преди да транскодираме отново. 
// Worker — процесира един job
async function processTranscodeJob(job) {
  const { videoId, s3RawKey } = job;

  // Idempotency check
  const exists = await s3.exists(
    `${videoId}/720p/segment-000.ts`
  );
  if (exists) return; // вече направено!

  // Download raw video
  await s3.download(s3RawKey, `/tmp/${videoId}`);

  // Transcode all resolutions IN PARALLEL
  await Promise.all(RESOLUTIONS.map(r =>
    transcodeToHLS(videoId, r.name, r.size, r.bitrate)
  ));

  // Generate master manifest
  const manifest = buildMasterManifest(videoId);
  await s3.put(
    `${videoId}/manifest.m3u8`, manifest,
    { cacheControl: 'public, max-age=300' }
  );

  // Update DB + Invalidate CDN cache
  await db.setVideoReady(videoId);
  await cdn.invalidate(`/${videoId}/manifest.m3u8`);
}

  for (const key of keys) {
    const count = await redis.getdel(key);
    const videoId = key.split(':')[1];

      WHERE id = $2

Recommendation System — Two-Stage Neural Network

Защо е важна: Препоръчителната система отговаря за 70%+ от общото watch time на YouTube. Без нея потребителите щяха да напуснат след първото видео. Това е една от най-сложните ML системи в света.
🎯
Основният Проблем

От 800+ милиона видеа, изберете точно тези 20 които ще покажат на конкретен потребител в неговия home feed. И го направете за <100ms. За всеки от 2.5B потребителя. На всяко зареждане на страница.

🏗️ Two-Stage Architecture
┌─────────────────────────────────────┐ │ 800+ MILLION VIDEOS │ │ (entire YouTube corpus) │ └──────────────┬──────────────────────┘ │ ▼ ┌──────────────────────────────────────────────┐ │ STAGE 1: CANDIDATE GENERATION │ │ ───────────────────────────── │ │ Deep Neural Network │ │ Input: user history, demographics, topics │ │ Output: ~500 candidate videos │ │ Goal: RECALL (find anything relevant) │ │ Speed: ~10ms │ └──────────────┬───────────────────────────────┘ │ ~500 candidates ▼ ┌──────────────────────────────────────────────┐ │ STAGE 2: RANKING │ │ ───────── │ │ Deeper Neural Network │ │ Input: rich video + user features │ │ Output: scored & sorted top 20 │ │ Goal: PRECISION (best of the best) │ │ Speed: ~50ms (per candidate, parallel) │ └──────────────┬───────────────────────────────┘ │ ▼ ┌──────────────────┐ │ TOP 20 VIDEOS │ │ shown in feed │ └───────────────────┘
1️⃣
Stage 1: Candidate Generation

Не можем да оценим всичките 800M видеа за един потребител — твърде бавно. Затова първо отсяваме до ~500 кандидата.

Inputs (User Embedding):
  • Watch history — embeddings на последните гледани видеа
  • Search history — embeddings на последните търсения
  • Demographics — възраст, пол, локация, език
  • Example age — кога потребителят е активен (за свежест)
  • Device & context — мобилен/десктоп, час от деня
Approach: Embedding Retrieval

Всеки потребител и всяко видео получават vector embedding в едно високо-измерно пространство. Близки vector-и = близки интереси. Използва се approximate nearest neighbor search (HNSW/ScaNN) за бързо намиране на най-близките видеа.

Content ID — Copyright Detection at Scale

Защо е критична: Без Content ID, YouTube щеше да е залято с пиратско съдържание и щеше да бъде съдено в забвение. Системата сканира всеки upload срещу база от милиони copyright reference файлове за минути.
🔍
Как работи Content ID
Step 1: Rights Holders качват Reference Files

Музикални компании, филмови студия и TV мрежи качват техните оригинални работи. YouTube създава digital fingerprints (audio + video hashes) и ги съхранява в reference database.

Step 2: New Upload се сканира

Когато някой качи видео, Content ID извлича audio и video fingerprints. Те се сравняват с reference database — over 100 trillion comparisons per day.

Step 3: Match Action
Match TypeAction
Audio match (full song)Monetize (revenue → rights holder)
Video match (full clip)Block worldwide
Partial match (5 sec clip)Track (no action, just stats)
No matchPublish normally
🎵
Audio Fingerprinting

Audio се обработва на честотни spectrograms. Извличат се landmark hashes — характерни точки във времево-честотното пространство. Тези hash-ове са устойчиви на: pitch shifting, tempo change, noise, compression. 

// Concept (Shazam-style fingerprinting)

function fingerprintAudio(audioBuffer) {
  // 1. Compute spectrogram (FFT over time windows)
  const spectrogram = computeFFT(audioBuffer, {
    windowSize: 4096,
    hopSize: 2048
  });

  // 2. Find peak frequencies (landmarks)
  const peaks = findLocalMaxima(spectrogram);

  // 3. Pair peaks → unique hash
  const hashes = [];
  for (const [p1, p2] of pairAdjacentPeaks(peaks)) {
    const hash = combineHash(
      p1.freq, p2.freq, p2.time - p1.time
    );
    hashes.push({ hash, timestamp: p1.time });
  }

  return hashes;  // ~1000 hashes per minute of audio
}

// Database has billions of these hashes indexed
// Matching is O(log N) per hash via inverted index
🎬
Video Fingerprinting

Video fingerprinting е по-сложно. YouTube използва perceptual hashing — извличат се ключови кадри (keyframes), всеки се конвертира в нискомерен hash който е устойчив на: resolution change, color change, watermarks, mirroring, slight cropping.

Sequence-based matching: дори ако някой обърне кадрите или ги забави, последователността от hash-ове все още match-ва оригиналното видео.

Generic Design vs Real YouTube Stack

Защо тази секция е важна: Цялото guide дотук показа архитектура с генерични AWS компоненти (S3, Kafka, PostgreSQL). Това е стандартният начин на отговаряне в interview. Но реалният YouTube ползва Google вътрешни системи. Тази секция изяснява разликите.
📊 Side-by-Side Comparison
Component This Guide (Generic) Real YouTube Why Different
Object Storage AWS S3 Colossus S3 egress costs $0.085/GB. YouTube saves $100M+/yr with custom storage.
Database MySQL + Vitess Spanner + Bigtable Vitess started inside YouTube and is still used. Spanner for global consistency.
Message Queue Apache Kafka Google Pub/Sub Pub/Sub is fully managed by Google, integrates with their stack.
Transcoding FFmpeg on EC2 Custom VCU hardware Video Coding Units (custom ASICs) — 30x faster than CPU transcoding.
Video Codec H.264 VP9 + AV1 VP9 is royalty-free (Google created it). AV1 cuts bandwidth 30% more.
CDN CloudFront Google Global Cache GGC nodes inside ISPs — closer to users than any commercial CDN.
Cache Layer Redis Memcached + custom YouTube was an early Memcached user. Still uses it heavily.
Search Elasticsearch Custom (based on Google search infra) YouTube ranking is part of Google's broader search system.
Compute EC2 + ECS Borg → Kubernetes Borg was Google's internal predecessor to Kubernetes.
Languages Node.js / Java Python + C++ + Java + Go Python for backend logic, C++ for transcoding, Go for new services.
🎓
Защо учим Generic stack
  • В interview очакват AWS/общи технологии
  • Концепциите са универсални (sharding, caching, CDN)
  • Можеш да го имплементираш с публични облачни услуги
  • Real Google internals не са публични
  • Generic stack е по-преносим към други компании
🏢
Защо YouTube ползва custom
  • S3 egress е $0.085/GB — твърде скъпо при exabyte
  • Custom hardware дава 30x по-бързо транскодиране
  • Google вече имаше инфраструктура (Borg, Colossus)
  • Vendor independence — не зависят от AWS
  • Оптимизации за specific workload (video) не съществуват в S3

Interview Takeaway

В интервю никой не очаква да знаеш точно какво ползва YouTube вътрешно — те искат да видят че можеш да дизайнаш система от нулата със стандартни компоненти.

Но ако споменеш че знаеш разликата между generic stack и Google internal tools — това впечатлява interviewer-а. Можеш да кажеш: 

// Какво да кажеш в интервю

"Бих използвал Kafka за message queue, защото е стандартен 
и добре документиран. Реалният YouTube ползва Google Pub/Sub, 
но концепцията е същата — async processing с ordering guarantees."

"За storage бих избрал S3 — durable, скалируем, добре известен. 
YouTube построиха Colossus, защото S3 egress costs ($0.085/GB) са 
прохибитивно скъпи при exabyte мащаб. Но за обичайно приложение, 
S3 е правилният избор."

"За database — MySQL + Vitess. Това всъщност е реалното YouTube 
решение, защото го построиха инхаус и го open-source-наха. 
Спестява много операционна сложност."
